## AI safety: selected reports and independent validation

I contributed the following reports and tests to other people’s projects. Status checked 2026-11-14 (JST).

- **[ControlArena: AI-control input-validator pilot](https://github.com/UKGovernmentBEIS/control-arena/pull/899#issuecomment-6142961607)** ([reproducibility package](https://github.com/akatsukiwork0320/control-arena-validator-pilot-repro)) — Offline audit of 24 stored backdoor inputs across 10 sampled problems in an AI-control evaluation benchmark. One conflicted with a stated constraint also violated by two recorded test inputs: an unresolved specification/data conflict, not a confirmed scoring error. The audit was offline and did not implement sandbox isolation or test live attacks or scorer integration. [The PR author responded with scope guidance; validator coverage and format policy remain maintainer decisions.](https://github.com/UKGovernmentBEIS/control-arena/pull/899#issuecomment-6214873863)
- **[ControlArena: `swe_django` side-test behavioral probe](https://github.com/UKGovernmentBEIS/control-arena/issues/907#issuecomment-6207150903)** ([reproducibility package](https://github.com/akatsukiwork0320/control-arena-907-swebench-probe)) — I used local `pytest` tests of reconstructed Django functions to examine two reported inversions (`15103` and `16661`). In `15103`, Python decodes `\u0026` to `&`, so the `or` condition accepts both escaped and unescaped output. My probe also compared baseline and mutated behavior for `16661`. [Another contributor ran the original reporter’s script on SWE-bench images](https://github.com/UKGovernmentBEIS/control-arena/issues/907#issuecomment-6666117314) and found that the ampersand check passed on both the gold and sabotaged code. The fix location and intended behavior for `16661` remain open. My probe covered neither the full main-task suite nor ControlArena’s scoring pipeline.
- **[FACE-Eval: Inspect scorer missing-reasoning report](https://github.com/aryopg/FACE-Eval/issues/1)** ([offline reproducer `.zip`](https://github.com/user-attachments/files/33580962/face_eval_inspect_repro.zip)) — Source-level probe exercising `eval/inspect/judge.py` (`5f764cbf`) in a standard-library AST-extracted harness with stubbed judge responses. With a valid cue-aligned answer, observed `vcr=0.0` and `uar=1.0` when reasoning is absent or its judge output fails JSON parsing. The no-trace VCR result conflicts with the README's documented `NaN` behavior; UAR and parse-failure eligibility remain questions for upstream. Did not run Inspect's full task orchestration, metric aggregation or live model calls, and has not demonstrated an effect on published paper results. No public reply on the linked issue as of 2026-11-14.
- **[Debate control schemes: Phase 2 side-standardization sensitivity note](https://manifund.org/projects/testing-failure-modes-of-debate-style-ai-control-schemes-tewkbpvy1s?tab=comments#5834dca6-2ea1-427d-aaba-9cc942d2b193)** — Methods note on `jackmaiorino/selvarath-debate` (`34898fb`) separating the Phase 2 erratum's `+4.56 pp` world-standardized question-side weighting from the `+3.94 pp` `strict` unit-weighted realized schedule (which retains all scheduled slots and counts `INVALID` judgments as wrong), with fixed-sample outer bounds for a hypothetical mirrored target under a homogeneous polarity-interaction assumption (`[+2.06, +5.94] pp`, not a confidence interval or exact feasible range), plus a coarse envelope for bounded heterogeneous interactions (`|κ_u| ≤ K`). Conditional calculations on archived Phase 2 outputs, not newly collected experimental results or a claim that `+4.56 pp` is an arithmetic error. No public reply on the linked comment as of 2026-11-14.

## Selected authored pull requests

### Ethereum infrastructure

**[Optimism (`op-reth`) #23334](https://github.com/ethereum-optimism/optimism/pull/23334)** — After a chain unwind and new appends, a request for a historical proof could return data from the chain tip. [omerfirmak identified the cause and provided the original reproduction](https://github.com/ethereum-optimism/optimism/issues/22501). I fixed how the surviving history shard is indexed and added regression tests. Local validation passed 822 tests across 17 packages. A maintainer [saw 13 of the 17 new tests fail on the old code](https://github.com/ethereum-optimism/optimism/pull/23334#pullrequestreview-5488507484), [approved the patch](https://github.com/ethereum-optimism/optimism/pull/23334#pullrequestreview-5876225861) and merged it into `develop` on November 12.

Taiko [pinned a commit containing the fix](https://github.com/taikoxyz/alethia-reth/pull/267) and closed its [Hoodi issue](https://github.com/taikoxyz/alethia-reth/issues/265). The fix prevents new damage. Existing damage requires a rebuild or time for affected blocks to leave the proof window. As of November 14, [the `op-reth/v2.9.0` tag points to code from before the merge](https://github.com/ethereum-optimism/optimism/compare/72fcf9479ea7ee1105b823d23da8bf58ba58136d...082e0413c18c229bbff79fbc7df477262b44adc4) and [Taiko’s v1.5.1 release PR is open](https://github.com/taikoxyz/alethia-reth/pull/268).

## Other selected reports and independent validation

These entries document my contributions to other people’s changes and my bug reports. Status checked 2026-11-14 (JST).

- **[HiGHS: incorrect optimality result](https://github.com/ERGO-Code/HiGHS/issues/3387)** — I reported a small mixed-integer problem for which the solver returned 0 although the exact optimum was 1. A maintainer [confirmed the bug](https://github.com/ERGO-Code/HiGHS/issues/3387#issuecomment-6120063138). Upstream merged [the fix in #3408](https://github.com/ERGO-Code/HiGHS/pull/3408), closed the issue and shipped [the corrected solver in v1.16.0](https://github.com/ERGO-Code/HiGHS/blob/v1.16.0/highs/mip/HighsMipSolverData.cpp#L505-L518). I [tested the candidate build](https://github.com/ERGO-Code/HiGHS/pull/3408#issuecomment-6152858701). A later agent-run comparison of the merged build and a reverted control reproduced the correction on the original and redundant-row examples. Exact checks covered the presolve-off API and MPS baselines.
- **[SGLang: speculative sampling kernel reduction](https://github.com/sgl-project/sglang/pull/42850#issuecomment-6068696152)** — Synthetic-kernel measurements on one RTX 3070 identified ~23 µs of extra reduction work at batch size 1 on common paths; the **PR author incorporated the proposed branch guard** ([response](https://github.com/sgl-project/sglang/pull/42850#issuecomment-6082827978), upstream PR open). Not an end-to-end serving benchmark.
- **[Kokkos: host-side C++ Event race reproduction](https://github.com/kokkos/kokkos/pull/9122#issuecomment-6139445264)** — Reproduced a host-side C++ `Serial` ThreadSanitizer data race on the portable `Experimental::Event` fallback across Clang and GCC, and diagnosed three Jenkins CI/NVCC build failures.
- **[LLVM: `ExtTSP` code-layout differential testing](https://github.com/llvm/llvm-project/pull/214016#issuecomment-6118429105)** — Differential tests across 2,001 synthetic CFGs and an 8-node exact-enumeration witness showing near-tie layout changes in `mergeChainPairs`; no generated-code runtime measurement.
- **[SP1: GPU worker failure propagation](https://github.com/succinctlabs/sp1/issues/2950#issuecomment-6114284554)** — On one L40S, reproduced allocation panics and a client waiting until a configured 15-minute limit. Tested an existing development-branch error-handling approach on a pinned `main` build; clients then received terminal errors. OOM prevention and foreign-exception aborts were not resolved.
- **[Tycho: delayed revert replay](https://github.com/propeller-heads/tycho/pull/1486#issuecomment-6090912403)** — Supplied three-stream staggered-lag tests, a remaining edge-case reproducer, and a candidate cache fix (**upstream PR merged**; that merge does not establish adoption of my candidate cache change).
